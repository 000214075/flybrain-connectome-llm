# 训练效率：实测成本模型与优化菜单

本文件是 2026-09-19 下午的一轮效率分析（主代理）。所有数字都标明是**实测**还是**估算**。
**本文件在写完后被我自己更正过一次**，见 §3（我把 `model.py` 当成了交付模型的 forward，实际那是混合
transformer 那条路；抓到错误的是训练日志里的 `32sweeps`）。

## 一、实测：扫描(sweep)的成本模型

真实 MaleCNS 连接组（164,587 神经元 / 25,563,096 突触），`torch.sparse.mm`（CSR、
`check_invariants=False`、fp32、与训练同路径），测不同批宽下单次扫描耗时：

| 批宽 | ms/扫描 | 按 CSR 字节（205 MB）折算 | ms/扫描/列 |
|---|---|---|---|
| 16 | 12.163 | 16.8 GB/s | 0.7602 |
| 32 | 22.391 | 9.1 GB/s | 0.6997 |
| 64 | 36.168 | 5.7 GB/s | 0.5651 |
| 128 | 68.349 | 3.0 GB/s | 0.5340 |
| 256 | 117.804 | 1.7 GB/s | 0.4602 |

线性拟合 **ms/扫描 ≈ 5.1 + 0.44 × 批宽**：

- **固定项 A = 5.1 ms**：只读 CSR 结构（`base` 102 MB + `col` 102 MB）跑出 **~40 GB/s**，
  即本卡 960 GB/s 峰值的 **4%** —— 行长尾造成的负载不均。
- **每列项 B = 0.44 ms**：折算 **~464 GB/s ≈ 峰值的 48%**，这一项已接近硬件上限。

**入度分布（同数据实测）**：mean 155.3 / median 100 / p90 320 / p99 862 / **max 11,526**；
前 1% 的行占 8.9% 的边，前 10% 占 36.4% ⇒ 一行一线程的内核被最长的那几行拖尾，这就是 A。

## 二、实测：一次训练步做 64 次扫描，且**扫描就是全部成本**

交付模型是 `src/flybrain/connectome_lm.py` 的 `ConnectomeLM`，它的 forward 是逐位置递推
（`connectome_lm.py:112-122`）：

```python
for position in range(t):
    state = self.brain.advance_drive(state, drives[:, position])   # 一次扫描
    logits.append(self.head(self.brain.read_latent(state)))        # 读一次
```

`context: 32` ⇒ **前向 32 次扫描**，反向同样 32 次 ⇒ **每步 64 次扫描**。
训练日志每一步都打印 `32sweeps`（`brain.sweeps` 计数），与之一致。

**成本模型对账**：

```
步时 ≈ 64 × (5.1 + 0.44 × 32) ms = 64 × 19.2 = 1227 ms
实测步时 = 1217 ms（1.2168 s/步，step 6900 那次）
⇒ 误差 0.8%
```

**⇒ 扫描占了这一步的几乎全部时间。** 稠密部分（`up`/`read_down`/`head`）是零头：
吞吐 884 tok/s = 1024 token/步 ÷ 1.217 s，与 64 × 19.2 ms 的预测吻合。
（我最初的微基准单次扫描是 22.4 ms，比反推的 19.2 ms 慢 17%——因为它是在长臂占着卡的时候跑的。）

## 三、⚠️ 更正我自己的一处错误结论（已作废）

**我曾写下**："`brain_chunks: 1` 让 32 个 token 被 mean-pooling 成一个向量、只扫一次、读出版本广播给
所有位置 ⇒ 每个位置 logits 相同，所以模型无法区分词序。"

**这是错的，已作废。** 反证：

1. `brain_chunks` / `max(1, t // brain_chunks)` 那一行属于 **`model.py` 的 transformer 路径**
   （那条路确实用 `wholebrain.py:761` 的 `_drive`，其中有 `norm_in(x).mean(dim=1)`）。
   交付模型走的是 **`connectome_lm.py` 自己的 forward**，它**逐位置**调用
   `advance_drive(state, drives[:, position])`，传进去的是 `(B, n_neurons)` 的**二维**驱动，
   **不经过 mean-pooling**。
2. 训练日志每一步都写着 **`32sweeps`**，即前向 32 次扫描——如果真的只扫 1 次，这里会是 1。

**教训**：`model.py` 与 `connectome_lm.py` 都有 `forward`，且 `model.py` 的更长、更像"主模型"。
**判断交付路径前先确认是哪个类**；这次的判别证据来自**训练日志的计数字段**，不是读代码的直觉。

**对"质量为什么低"的影响**：这一条解释作废，`brain_chunks` 也**不是**速度/质量的共用旋钮。
质量归因回到那些已经实测过的因素：ppl 37.90、18000 步只覆盖语料 45.6%、`brain_rank` 用 256（未饱和）、
`context` 只有 32、语料 4,039 万 token 偏小。**"扫描一次看全序列"不是原因。**

## 四、成本结构意味着什么（速度）

由 §一 的模型，步时 ≈ `64 × (5.1 + 0.44 × batch)`：

| 方案 | 步时（估算） | 吞吐 | 相对现状 |
|---|---|---|---|
| 现状 batch 32 | 1227 ms | **841–884 tok/s**（实测） | 1× |
| batch 64 | 64 × (5.1 + 28.2) = 2131 ms | 961 tok/s | **+14%** |
| batch 256（显存放不下） | 64 × 117.8 = 7540 ms | 1087 tok/s | +29% |

**关键结论：成本几乎正比于"扫描次数 × 批宽"，也就是正比于 token 数。**
固定项只占 27%，所以**加批宽几乎不会提高吞吐**（每列那 0.44 ms 才是主项，而它已经跑到峰值的 48%）。
⇒ **靠调度/批宽最多拿到 ~1.3–1.5×**。

**真正的大杠杆只有一个：减少边的数量（或减少扫描次数）。**

- **扫描次数**由因果性决定：预测第 k 个 token 必须先把前 k 个 token 折进去，因此每 token 一次扫描，
  这是架构决定的，改不了（除非改掉"逐 token 递推"本身，那就不再是这个模型）。
- **边数**可以减：25.5M 条边里，入度 median 只有 100、mean 155，说明长尾很宽。
  按键（权重×符号）保留每神经元 top-k 输入：k=64 ⇒ 约 164587×64 ≈ 10.5M 条边 ⇒ **扫描成本约 0.41×**。
  这是**唯一一条能把 1.2 s/步降下来的路**，而且是**近似线性**的。
  **代价**：模型语义改变（仍是这份连接组的强连接子图，但已不是全部突触），
  **必须用同一条固定 24 批命令测质量代价**。

## 五、优化菜单（按优先级）

| # | 动作 | 依据 | 预期 | 状态 |
|---|---|---|---|---|
| 1 | **突触剪枝 top-k（k=32/64/128）** | §一 的入度长尾；成本 ∝ 边数 | 边数降到 0.4× ⇒ **步时约 0.4×**；质量代价未知 | **未做**，需要空闲 GPU |
| 2 | **按入度分箱调度**（自行实现：把行按度数分箱，每箱单独构造子 CSR 再 `sparse.mm`） | 文献 §7.9 的"粗粒度两级分箱"；针对固定项 A | A 从 5.1 ms 压到 ~1 ms ⇒ 步时 −21%（batch 32） | **未做**，需要空闲 GPU |
| 3 | 批宽 64 | §一 的拟合 | **+14%**，但需重调 lr，且改变可比性 | 未做 |
| 4 | `csr_base` 用 bf16 | —— | **已被否决**：本 ROCm 版对 bf16 稀疏矩阵乘直接 `hipsparseSpMM not implemented`（`wholebrain.py:508`） | 不再考虑 |
| 5 | 缓存 sparse 张量对象 | —— | 每步只构造 64 次、单次开销 <0.1 ms ⇒ **<1%，不做** | 不做 |
| 6 | 换 4×A800 等多卡 | 见对话中的带宽比较 | 2.1×/卡（带宽比），但需先写 DDP | 属于硬件决策 |

**质量（"智能程度"）的杠杆**（本文件不重复展开，均为本项目已实测）：

1. **更多步数/epoch**：77.1 MB / 4,039 万 token，18000 步只覆盖 **45.6%**；9000→18000 步仍在降
   （3.9245 → 3.6349）。
2. **`brain_rank`**：固定 600 步下 128/256/512/1024 → ppl 339.1 / 201.5 / 134.0 / 99.45，**未饱和**。
3. **语料规模**：40M token 偏小；`src/flybrain/teacher.py` 具备用教师 API 扩语料的能力。
4. **context**：canonical 只有 32（混合模型当年用 512）。**注意**：扫描次数 = context（每 token 一次），
   所以加长上下文会让步时**线性上升**——这是真正的速度/质量权衡处。
